# Frontend Build Prompt

*Fill out this brief and give it to the AI with [1. Project Scope](1.%20Project_Scoping_Prompt.md) and any wireframes. No ongoing Markdown updates are required.*

## 1. Screens & Design

- **Framework / platform:** [What will you use to build the frontend? Use the choice from scope, e.g., React for web or Flutter for mobile.]
- **MVP screens and navigation:** [Which screens are needed, and how does the user move between them? e.g., Task list → Create task form → Submit → Updated task list.]
- **Design references:** [What should the app look like? Add wireframes, screenshots, or links; e.g., a Figma link or a reference app's task list.]
- **Theme / shared components:** [Which styles and controls should be consistent? e.g., dark green theme, Inter font, shared buttons, text inputs, and bottom navigation.]
- **Target layouts:** [Where should the UI work? e.g., Android phones only, or phone and desktop browsers.]

## 2. Data & Connection

- **Inputs / results needed:** [What does each action send and display? Use scope's initial plan; e.g., Create task sends a title and displays the returned id, title, and status.]
- **Starting data:** [Will screens use mock data or an existing backend first? e.g., Start with three mock tasks, then replace mocks with real calls.]
- **Authentication:** [Does the UI need sign-in, and what happens when the session expires? e.g., Email/password login; expired sessions return to login. Write none if not needed.]
- **Client setup:** [What connection details are available? e.g., API base URL or Supabase project URL and public variable names such as NEXT_PUBLIC_SUPABASE_URL. No secrets; write TBD if the backend is not ready.]

## 3. Build Instructions

- Build only MVP screens and client-side integration. Follow existing code, reuse theme tokens/components, and preserve unrelated changes.
- Keep network calls in a separate API client/data adapter. Use the same interface for mocks and real data.
- Handle loading, empty, success, validation, and service-error states. Guard duplicate submissions and use accessible controls.
- Inspect implemented backend interfaces before wiring them. Resolve missing details and communicate interface changes directly; update affected code and mocks together.
- Connect the first real journey early. Verify the visible result, failure feedback, and persistence where needed.
- Summarize changes, run/setup instructions, checks, and remaining mocks/blockers. Distinguish mock, local, browser/device, and hosted results.
