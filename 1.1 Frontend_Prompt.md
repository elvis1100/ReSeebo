# Frontend Build Prompt

*Fill out this brief and give it to the AI with [1. Project Scope](1.%20Project_Scoping_Prompt.md) and any wireframes. No ongoing Markdown updates are required.*

## 1. Screens & Design

- **Framework / platform:** Flutter with Dart. All screens must work fully offline from first launch; use the suggested packages and boundaries in project scope.
- **MVP screens and navigation:** Receipt/product list → Scan or import → Review and match → Save → Product comparison/history. Show suggested selling prices and estimated gross profit alongside purchase costs; put optional restock quantity and markup/selling-price controls on the comparison screen. Show supplier-grouped buying estimates when quantities are entered.
- **Profile / product editing:** Add a local store profile editor for store name, optional owner name/photo/logo, and default markup. Allow product photo capture/gallery selection, optional barcode/category, markup override, and owner-set selling price. Use one optional photo per product with a placeholder when absent. Profile setup must not block scanning; prompt for markup when pricing suggestions need it.
- **Design references:** [Idea document](SARI-SARI-RECEIPT-IDEA.md), especially its workflow and comparison tables. Visual references/wireframes: TBD.
- **Theme / shared components:** Palette and typography TBD. Reuse Flutter theme styles, buttons, form fields, product/supplier selectors, and comparison rows. Show ₱ amounts, quantity units, and purchase dates consistently. Use labels as well as colors for price changes.
- **Target layouts:** Phone portrait layout, with comparison tables/rows adapted to narrow screens. Demo OS/device: TBD. Verify on the actual phone; the proposed OCR integration targets Android/iOS.

## 2. Data & Connection

- **Inputs / results needed:** Profile/product edits and selected photos → locally saved details and file references. Image → editable receipt draft; corrected supplier/date/product/quantity/amount fields and confirmed aliases → saved receipt/mappings. Product selection → dated supplier comparison/history, suggested selling prices, and gross profit. Optional restock quantities or pricing adjustments → updated estimates. Exact interfaces come from the integration owner.
- **Starting data:** Small illustrative fixtures matching agreed Dart types for initial layout work, then real local services. Use receipts covering two suppliers, repeated purchases, and a same-day comparison. Clearly distinguish fixture demonstrations from real recognition/persistence.
- **Authentication:** No accounts or sign-in in the current scope.
- **Client setup:** Use local Dart service adapters backed by SQLite and persistent image files. Bundle fonts, icons, and other UI assets; screens must not depend on remote resources.

## 3. Build Instructions

- Build only MVP screens and client-side integration. Follow existing code, reuse theme tokens/components, and preserve unrelated changes.
- Keep local service calls behind adapters. Use the same agreed interface for mocks and real local data; keep parsing/calculations out of widgets.
- Show the original receipt during review; allow correction of missing/unclear fields and confirmation of product matches before saving.
- Offer matches from saved product aliases, with owner confirmation for ambiguous descriptions. Show supplier branch/location where needed to distinguish rows.
- Make tables the primary insight format. Include supplier, purchase date, comparable unit cost, differences, and receipt references. Separate latest recorded prices from lowest historical prices; highlight unknown data without inventing values.
- In history, compare with the previous purchase of that exact product at the same supplier. Keep same-day purchases separate. If ordering is ambiguous, expose the records and resolve the selection rule with the integration owner.
- Use a product's markup override when set (including 0%), otherwise the owner-selected store default. Keep calculated suggested selling price and optional owner-set selling price clearly labeled; calculate estimated gross profit against the displayed purchase cost. If markup is unset, request it instead of assuming a percentage. Buying suggestions use recorded prices and show dates, quantities, totals, and extra costs. Sentence summaries are optional.
- Handle loading, empty, success, validation, and service-error states. Guard duplicate submissions and use accessible controls.
- Inspect implemented local service interfaces before wiring them. Resolve missing details and communicate interface changes directly; update affected code and mocks together.
- Connect the first real journey early. Verify first launch, scanning, review, saving, comparisons, and calculations with internet disabled. Check failure feedback and that profile, product photos, aliases, pricing settings, and receipts/images survive app restart.
- Summarize changes, run/setup instructions, checks, and remaining mocks/blockers. Run `flutter analyze` and appropriate focused checks once code exists. Distinguish fixture UI, real local storage, and physical-device offline OCR results.
