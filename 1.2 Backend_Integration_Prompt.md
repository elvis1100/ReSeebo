## 1. Backend & Data

- **Backend / BaaS / database:** Supabase PostgreSQL/Auth and optional private Storage for online backup. On-phone Dart services and SQLite (`sqflite` suggested) handle the core workflow. No FastAPI or cloud inference required.
- **MVP operations:** Recognize an image and return an editable receipt draft; atomically save a confirmed receipt and purchase lines; list local receipts/products; return dated supplier comparisons/history; calculate restock and selling-price estimates. A separate signed-in operation backs up confirmed records/images to Supabase. Exact method names/types: TBD.
- **Initial entities:** Products and Suppliers are reusable identities. Receipts reference suppliers; purchase lines reference receipts and products, preserving original descriptions, confirmed quantities/pack conversion, net amounts, and unit costs. Each purchase is separate, including same-day purchases. Supabase copies carry owner IDs and stable record IDs. Follow the provisional entities in project scope.
- **Rules / permissions:** Require confirmation of unresolved fields. Match the exact brand/variant/size; never silently merge different products. Validate quantities and amounts before calculating unit costs. Keep earlier purchases; compare supplier changes against the previous purchase at that supplier. Resolve ambiguous same-day ordering explicitly. Local use works without login; Supabase database and image policies restrict backup access to the signed-in owner.

## 2. Services & Setup

Put cloud schema/policies in Supabase migrations. Provide actual local and hosted backup setup separately when implemented.

## 3. Build Instructions

- Inspect existing code, preserve unrelated changes, and build only MVP local services/backup integrations. Refine the schema as needed; keep OCR, receipt parsing, models, calculations, local storage, and Supabase adapters separate.
- Enforce purchase validation at the local service/database boundary and ownership at the Supabase database/Storage boundary. Keep secrets out of code/logs; make repeated saves and backup retries safe from duplicate records. Surface possible duplicate receipt imports for confirmation.
- Define exact interfaces in Dart models/services and migrations/policies. Preserve price/quantity snapshots per purchase. Use consistent money units and rounding; handle net amounts/discounts without counting discounts twice.
- Compare latest recorded purchase prices per supplier with dates visible; historical minima remain a separate view. Missing prices, pack sizes, or availability remain unknown. Restock calculations respect whole packs and show owner-entered extra costs; do not claim guaranteed current prices or maximum profit.
- Suggest suppliers for selected products using the latest comparable records and group the list by supplier. Show estimated totals and the data's dates; separate product-price savings from travel/delivery costs. Mark selling-price outputs as estimated gross profit, with adjustable markup.
- Preserve local receipt images in persistent app storage. Local saves must succeed independently of cloud backup. Keep stable IDs for repeatable backup; automatic bidirectional sync and restore are outside the first MVP unless separately agreed.
- Resolve missing interface details before frontend use. Coordinate caller-visible changes directly and update affected code/fixtures together.
- Provide working operations and setup examples; frontend work handles client wiring. Prove OCR on a real phone with internet disabled early, then verify confirmed saves survive restart and appear in comparisons. Verify backup ownership and retries separately when online.
- Summarize changes, setup, checks, and blockers. Run `flutter analyze` and appropriate focused tests once code exists. Distinguish service-only/static checks, connected local storage, real-device offline OCR, and hosted Supabase backup results.
