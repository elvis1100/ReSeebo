# Backend & Integration Build Prompt

*Fill out this brief and give it to the AI with [1. Project Scope](1.%20Project_Scoping_Prompt.md). A full schema is not required upfront; no ongoing Markdown updates are required.*

## 1. Backend & Data

- **Backend / BaaS / database:** [What will handle server logic and storage? Use the choice from scope, e.g., Supabase with PostgreSQL, or FastAPI with PostgreSQL.]
- **MVP operations:** [Which actions must the backend support, and what do they receive/return? e.g., Create task accepts a title and returns id, title, and status; list tasks returns the user's tasks.]
- **Initial entities:** [What needs to be stored, and how is it related? e.g., Users and Tasks; each task belongs to one user. Unknown fields can remain TBD.]
- **Rules / permissions:** [What must be validated, and who can access the data? e.g., Task titles cannot be empty; users can view and edit only their own tasks.]

## 2. Services & Setup

- **External services:** [Which outside services does the MVP need, and why? e.g., An AI API to summarize task notes. Write none if not needed.]
- **Configuration:** [Which environment variable names are needed, and which are server-only? e.g., NEXT_PUBLIC_SUPABASE_URL for the client; DATABASE_URL and OPENAI_API_KEY on the server only. Do not enter secret values.]
- **Local setup:** [How will you start the backend and prepare its database? e.g., Backend start command, migration command, and API URL. Use the actual stack's commands when known; otherwise write TBD.]
- **Example calls:** [How can someone try an operation once it works? e.g., A curl command that creates a task, its expected response, or the path to a runnable request example. Write TBD until implemented.]

## 3. Build Instructions

- Inspect existing code, preserve unrelated changes, and build only MVP backend/integrations. Refine the schema as needed; keep services, models, and external adapters separate.
- Enforce rules and permissions at the server/database boundary. Keep secrets out of code/logs; handle service failures and make retries safe from duplicate writes where relevant.
- Define exact interfaces in routes, schemas, types, or BaaS queries/policies. Direct BaaS access makes exposed tables/policies part of the frontend interface.
- Resolve missing interface details before frontend use. Coordinate caller-visible changes directly and update affected code/fixtures together.
- Provide working operations and setup examples; frontend work handles client wiring. Coordinate an early real journey check covering result, persistence, errors, and permissions where applicable.
- Summarize changes, setup, checks, and blockers. Distinguish backend-only, connected local, and hosted results.
