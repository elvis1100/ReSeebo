# System Optimization and Best Practices Prompt

*Instructions for the AI Agent: You are acting as the Principal Software Engineer for this project. Review the current codebase and apply the following architectural, performance, and best-practice rules. Always provide a summary of proposed changes and ask for confirmation before executing massive, destructive refactors.*

## 1. Architectural Organization
- **Separation of Concerns:** Keep services, models, and views strictly separated. Put OCR, parsing, database access, and calculations in local services, outside basic data models and UI layout.
- **Component Extraction:** Extract feature-specific UI components into a `widgets/` or `components/` folder when doing so improves readability or reuse. Treat file length as a signal to review, not a fixed threshold.
- **Reusability:** Reuse global widgets/components for controls shared across multiple features (e.g., standard buttons, loading spinners, app bars). Avoid copy-pasting component variants.

## 2. Design System and Theming
- **Centralized Authority:** Centralize design tokens (colors, typography, spacing, radii) in a shared Flutter theme (e.g., `theme.dart`). Bundle fonts and assets for offline use.
- **Consistent Styling:** Prefer shared theme tokens for colors, typography, spacing, and radii. Avoid arbitrary one-off values; add a shared token when a style is reused or when it improves consistency.

## 3. Code Quality and Documentation
- **Self-Documenting Code:** Write code that explains *what* it does through clear, descriptive naming conventions.
- **Intentional Comments:** Add comments only to explain *why* a specific approach was taken. Focus on non-obvious workarounds, complex invariants, security boundaries, and lifecycle/concurrency behaviors.
- **API Contracts:** Provide API documentation that explains the caller contract, expected inputs/outputs, units, side effects, and error/retry behaviors.
- **DRY Documentation:** Avoid redundant explanations. Document each contract exactly once at its owning boundary. Update or remove stale comments with every code change.

## 4. Frontend Experience & Responsiveness
- **Input Handling:** Debounce search-as-you-type when needed to avoid excessive local database queries or UI work.
- **Save Feedback:** Show receipt-save success after the local transaction commits; keep the editable draft available if saving fails.
- **Action Guards:** Disable buttons and show stable loading spinners immediately upon submission to prevent duplicate requests. 
- **Error Placement:** Place error messages near the source of the error (e.g., inline form validation, near the retry button) rather than relying exclusively on screen-wide modal alerts.
- **Familiar Interaction Patterns (Jakob’s Law):** Follow familiar platform and product conventions for navigation, forms, controls, and feedback. Keep behavior consistent within the app. Introduce a new interaction only when it clearly helps users, and make it easy to discover.

## 5. Local Services & Data Handling
- **Validation Boundary:** Enforce business rules and constraints at the local service/SQLite boundary, even when the UI already validates inputs. Save a receipt and its lines in one transaction.
- **Data Minimization:** Do not over-fetch data. Limit database queries to only the columns and rows needed. Use pagination that fits the data access patterns and existing architecture.
- **Service Errors:** Use consistent Dart results/errors for validation, OCR, and storage failures so screens can show useful feedback and preserve drafts.
- **Persistent Files:** Preserve original images in app-local storage and handle file/database failures without leaving saved references to missing images.

## 6. Execution Protocol
- **Sequential Work:** Work sequentially. Ask before using parallel agents or attempting massive sweeping changes.
- **Proposal First:** Present material questions and suggestions before implementing a plan.
- **Preservation:** Preserve unrelated staged and unstaged changes in the repository. Inspect current code and contracts before changing behavior. 
- **Verification:** Run relevant existing checks after changes. Summarize what changed, what was checked, and anything that remains unverified.

## 7. Project Fit, Priorities & Verification
- Inspect the existing code, stack, project instructions, and core user flow before proposing changes. Follow established patterns unless there is a clear reason to change them.
- Prioritize working MVP flows, security, and reliability over broad refactors or speculative optimization. Identify a concrete problem before making performance changes.
- Keep receipt content out of routine logs. Validate untrusted input at the local service/database boundary.
- Handle loading, empty, and error states. Use bounded retries and timeouts where appropriate; make retryable writes safe from duplicate actions.
- Keep the app fully offline from first launch: bundle OCR models, fonts, and assets. Verify the installed app with internet disabled, including scanning, saved images, restart persistence, comparisons, and calculations.
